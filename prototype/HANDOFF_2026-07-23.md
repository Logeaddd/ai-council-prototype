## 0. Purpose and truth standard

This document is for the next person taking over AI Council. It records the repository's observed state as of 2026-07-23, including unfinished local work and failures reported from the actual application.

Do not interpret a green unit test, a `passed` campaign report, or an existing installer as proof that the product can autonomously complete arbitrary user projects. The product has repeatedly failed real tasks after earlier work was described as complete. Every claim below is therefore labelled by evidence level:

- **Committed**: present at `HEAD` and recoverable from Git.
- **Local, uncommitted**: present only in the current worktree; it will be lost by a careless reset/clean.
- **Partially tested**: a narrow test was reported or inspected, but the complete suite was not rerun in this handoff session.
- **Unverified / known risk**: must not be represented as working until a real end-to-end run proves it.

The product goal is not to make a model's subjective output look polished. It is to provide the physiological capabilities of an autonomous local project worker: retain task context, read/write files, use real shell/network/package/tool/MCP/skill capabilities, acquire missing tools, build and verify artifacts, collaborate without losing state, survive interruption, and report failure honestly rather than presenting a green completion state.

## 3. Product architecture

### User-facing path

1. Electron starts `desktop/main.mjs` and the local server.
2. The renderer sends user work through the real HTTP API and reads Server-Sent Events (SSE).
3. `src/server.js` calls `runCouncilEvents` in `src/discussionEngine.js`.
4. The engine persists group/session state, creates member contexts, asks providers, executes tool requests, streams events to the UI, and runs finalization.
5. Sessions, public events, tool results, file operations, memory, usage, and runtime state live under the configured group workspace.

The CLI exposes the same core execution system through `src/cli.js`. Important commands include `real-user-baseline` and `real-user-campaign`; these are intended to drive the actual HTTP/SSE path rather than calling a model helper directly.

## 5. Important history and design decisions

### 5.1 The product is not a Forge/JAR-specific automation

The Minecraft Forge task was a diagnostic example, not the product definition. Earlier implementation overfit to `jar` delivery and failed to give agents a general route to acquire missing runtimes/tools. The intended general execution loop is:

`understand requested work -> inspect workspace/environment -> acquire missing tool or runtime -> perform real work -> build/run -> diagnose failures -> repair -> verify actual artifact -> report evidence`

This applies to JARs, PDFs, DOCX/XLSX/PPTX, scripts, code projects, archives, data files, and external workspace edits. Avoid adding task-specific branches just to make a benchmark pass.

### 5.2 No fabricated acceptance

Mock providers and simulated tool adapters are useful for deterministic unit tests only. They are not proof that the desktop product works. A previous error was treating local tests and synthetic PDF bytes as proof of autonomous delivery. The handover owner must maintain a hard distinction between:

- fast unit/integration tests: regression detection;
- local real-tool tests: validate filesystem/process/network/tool mechanics;
- paid real-provider HTTP/SSE campaigns: validate agent physiology and recovery;
- human quality review: subjective content/design quality, explicitly not scored as an automatic pass.

### 5.3 Limits are not a substitute for repair

The user rejected fixing tool loops merely by lowering a tool iteration cap or declaring an agent unavailable. The expected behavior is to detect *lack of progress*, preserve checkpoint/state, give the agent a useful continuation context, and either make progress or stop once with a truthful reason. Model-call/cost limits can exist for explicit budget protection; they must not be presented as a capability solution.

### 5.4 Context plan that remains to be completed

The agreed direction is original-file extension, not a LangGraph rewrite or a parallel memory stack:

1. **T111 Context receipt**: record exact injected sources, token/budget share, omissions, dedupe/shortening, conflicts, selection reason, and stable source pointers.
2. **Real context pressure baseline**: run the actual `buildMemberContext` on constructed/retained long histories; no mock model scoring. Measure retrieval, stale-instruction suppression, duplicate injection, and receipt explainability.
3. **T112 policy/invalidation**: introduce explicit priority and supersession/tombstone handling so obsolete user instructions or stale role statements cannot revive.
4. **T113 short-term working memory**: only add a replaceable member work cache if receipts/pressure data show it is necessary; it must not be an append-only second history.
5. **T114 retrieval audit**: structured filters already exist. Audit their coverage/performance first; add FTS5 only if measurement demonstrates a lexical retrieval deficit. Do not claim FTS5 currently exists.
6. **T115/T116**: extend retrieval/semantic search only against measured recall failures, then rerun pressure baselines.
7. **T117/T118 real-user survival matrix**: periodic/release gate via actual HTTP/SSE and a real provider, with machine-verifiable physiological oracles.

The numbering appears in `config/product-harness.json` for T105/T106/T117 only; the T111–T116 names above are the accepted planning vocabulary, not all completed tickets.

### 5.5 Real-user acceptance philosophy

The test question should be random and diverse, but automatic assessment must only check things that have a machine oracle. Examples: a file exists in the requested location; a PDF parses and includes actual referenced images/text; an archive can be extracted; a CLI runs; a Git commit exists; a configured MCP actually answers; a resumed session applies a later edit. Do not use an AI judge to assert whether a report is "good".

The task script can be seed-reproducible while provider output is not. A seed reproduces the task, follow-ups, interruptions, and role/name perturbations; it cannot guarantee the same provider text.

## 7. Known user-visible failures that must remain visible

### 7.1 Rabbit-mod illustrated PDF task failed

The reported live task was: research Minecraft rabbit mods, create a complete illustrated PDF, and place it on the desktop. The observed conversation repeatedly issued web searches and `skill` calls without writing, composing, producing, or verifying a real output. It looked like parallel independent activity, not coordinated delivery.

Do not dismiss this as an individual model's weakness. It exposed system-level deficiencies:

- the delivery state did not force an owner to move from research to production;
- the whole group could repeat overlapping searches;
- nonexistent/unavailable skill use was retried rather than becoming a repair branch;
- no end-to-end proof was demanded for an illustrated PDF at the requested external path;
- the test suite's `%PDF-` header check is much weaker than the product task.

`src/skillPacks.js` contains a curated `openai-pdf` catalog entry referencing OpenAI's public skills repository at a pinned commit. It is not a local "fake PDF generator" by itself. However, the product must clearly distinguish: catalog listing, installation success, enabling for this group, instruction read success, actual available executables/libraries, and verified artifact generation. Repeated calls to a skill that is not installed/enabled/usable must not masquerade as progress.

### 7.2 Stalled search/empty-file loops

Earlier Forge attempts showed agents inspecting the same directory/files repeatedly, producing invalid JSON, and never writing core source. A general no-progress detector must recognize repeated state/tool signatures with no accepted file/artifact/checkpoint advancement, inject a concise recovery instruction with the actual obstacle, and preserve state for continuation. It must not silently consume rounds until a hard cap or show a final success.

### 7.3 History, private chat, and stream correctness

User reports included missing old user messages/member messages, private and group chat sharing input/send state, text disappearing while streaming, and scrolling not following the newest message. The product contains persistence/journal infrastructure, but these are not closed by the current worktree change. Treat UI/state synchronization, session restoration, and complete chronology as active acceptance requirements.

### 7.4 Context overflow and repeated rounds

The latest active defect is covered in section 8. A large current-turn tool result can overflow the context, and the old outer overflow path could fail to set the guard stop reason. This allowed repeated rounds and hid the true cause in final output.
